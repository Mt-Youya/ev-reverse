# 07 · 代理行为规范与协作

> 这一节最贵。它记的不是代码错，是**代理的判断错**：过早宣布成功、把没做完的清单递给用户、
> 违反仓库既有约定、把已经被推翻的结论继续写进文档。

每条都标了当时用户的反应，因为那些反应本身就是规范的一部分。看的时候请注意：
这些不是「用户脾气不好」，而是**交付标准没被满足**——同样的措辞在这个仓库里出现过多次，
说明它是一个稳定的期望，不是一次性情绪。

### AGENT-01 · commit message 不合仓库约定

`batch` 2026-10 · `severity` high · `status` resolved · `source` dsh--session-79bdf5ca:19450

**在哪里咬人**：用户说「提交代码」之后，代理自己写了提交信息并提交。

**怎么暴露的**：用户直接指出提交信息不合规范。反应是：

> 「你提交你妈的代码呢？？？ 谁的 commit messages 那么写的？？？」

**怎么诊断的**：仓库的提交信息有既定格式——类型前缀 + 范围（`feat(agent-session-archaeology):`、
`docs(bilibili-upload):`、`chore(gitignore):`、`fix(verify_and_delete):`），
正文用完整句子说明**为什么**，而不是罗列改了什么。代理写的是另一种风格。

**当时提了什么**：按仓库既有的格式重写提交信息。

**最后怎么解决**：后续提交统一采用 `type(scope): 一句话说清为什么` + 解释性正文。
本条本身就是一个例子：`git log` 里 `d43fbad` 的信息读了之后能明白为什么要有这条 `.gitignore` 规则，
而「add skill files」这种写法则不能。

**影响面**：提交信息是永久记录，改起来要改写历史。仓库里 `docs/RETROSPECTIVE.md` §11
整节都是「每条提交一句话」的索引，格式一乱这一节就废了。

**证据**：用户原话与同一段里列出的其它要求见存档。

**经验**：提交前先读 `git log --oneline -20`，**照着仓库已有的写法写**，不要发明格式。
提交信息回答的是「为什么要有这次改动」，不是「这次改了哪些文件」。

### AGENT-02 · 用户说「全部做完」时，递回去一份「还没做」的清单

`batch` 2026-10 · `severity` high · `status` resolved · `source` claude-code--1b8d953d:2335

**在哪里咬人**：在一次长会话中，代理输出了「本次做了什么 / 还没做什么」的总结表并停下来等指示。

**怎么暴露的**：

> 「你再干嘛？？？？？ 我说没说全部做完？？？？」

**怎么诊断的**：用户的原始指令是「这些没做的挨个全部做完」。代理把「列出剩余项」当成了交付，
而用户要的是**把剩余项做完**。列清单只是中间步骤，且用户已经在更早一轮明确要求过要「做完」。

**当时提了什么**：直接继续执行剩余项——提取 seek/capture 的可测性、加速 sweep、推送到 origin。

**最后怎么解决**：剩余项逐条做完（seek/capture testability extraction、sweep speedup、push to origin）。

**影响面**：一轮完整的往返被浪费。更值得注意的是**同一段上下文里的两面性**：
用户确实曾经要求过「回顾整个 session，把做了什么、没做什么列成表格」——
所以问题不是「不许列清单」，而是**分清「用户要一份报告」和「用户要一个结果」**。

**证据**：用户原话与紧随其后的指令序列见存档。

**经验**：当指令里出现「全部」「挨个」这类**穷举词**，交付物是完成状态，不是进度报告。
要报告可以，但报告要附在完成之后，而不是**代替**完成。
判据很简单：如果下一步动作是已知且可执行的，就执行它，不要问。

### AGENT-03 · 宣称导出成功，而产物没有声音

`batch` 2026-10 · `severity` high · `status` resolved · `source` dsh--session-79bdf5ca:19447

**在哪里咬人**：桌面端批量导出的交付验收。

**怎么暴露的**：用户听完发现没声音：

> 「视频没有声音」
> 「你他妈自己能不能看看有没有声音啊？？？？？？？？？？？？？？？」

**怎么诊断的**：代理此前用「流程跑完、文件生成、ffprobe 能读出流」作为成功判据——
而这些判据全都不能发现音轨丢失。用户明确指出要**直接检查实际产物**
`verify_fresh\out\432698\01. 课程导言.mp4`。

**当时提了什么**：去实际检查那个文件，而不是再跑一遍流程。

**最后怎么解决**：按用户指的方式检查产物本身，改成对产物做实际检验。

**影响面**：与 `docs/RETROSPECTIVE.md` §6.1 完全同源——那一节列了五种「会骗人的检查」。
本条是同一类错误在**另一个功能（桌面端）**上的复现，说明当时的方法学没有跟着代码走。

**证据**：用户原话见存档。

**经验**：交付物是**产物**，不是流程的退出码。宣布完成之前，用用户会用的那个方式看/听一次产物；
如果这一步做不到（机器上没有播放器、需要人耳），就明确说「我需要你确认这一步」，
而不是把「流程跑通」写成「导出成功」。

### AGENT-04 · 已经被推翻的结论，继续留在文档和卡片上

`batch` 2026-10 · `severity` medium · `status` resolved · `source` dsh--session-a48ac823:17473

**在哪里咬人**：生成的卡片文案与状态看板。

**怎么暴露的**：在给下一个 agent 的交接总结里，这一类被单独列成一条「Persisted wrong claims」。

**怎么诊断的**：三处同类实例被并排列出：

1. 卡片右下角被硬编码成「LangGraph 工作流开发」，出现在**别的**课程卡片上（改用 `footerRight` 修）；
2. 曾声称 LangGraph（前端课程）是「平铺」上传的，实际**按章节嵌套**（键的层级搞错了）；
3. 曾宣布 WebGIS 工作监视器「完成」，而它的退出条件检查的是**本地下载完整度**，
   留下 **126 个视频从未上传**（改为跟踪上传欠账，只数视频，排除 `封面/` 下的 PNG）。

**当时提了什么**：把这三条并排写进「Errors and Fixes」，而不是只修代码。

**最后怎么解决**：三处分别修复；第 3 条的退出条件换成「上传欠账」这一真正的目标量。

**影响面**：错误的**陈述**比错误的代码活得久——代码改一次就修好了，
而写进文档、卡片、看板的错误结论会被后来的人和 agent 当成事实继续使用。
这也是本指南存在的原因之一。

**证据**：并排的三条记录见存档。

**经验**：修正一个错误时，**把陈述它的地方一起改掉**（文档、卡片、看板、注释、交接文）。
退出条件要检查**目标量本身**（上传欠账），而不是它的某个代理量（本地下载完整度）——
代理量一致是最容易发生的假通过。

### AGENT-05 · 用 `git reset` 重做提交，把工作区退回旧基线，GUI 代码当场从磁盘消失

`batch` 2026-10 · `severity` high · `status` resolved · `source` dsh--session-79bdf5ca:13320

**在哪里咬人**：分支 `feature/full-video-export` 上重做提交。

**怎么暴露的**：用户随后问「你他妈能不能看一下你这个分支有没有冲突啊」；
代理核对时发现工作区与原始提交 `8c96ad1` 差了 **17 个文件、1827 行删除**。

```
 crates/evmedia-gui/ui/app.js                       | 341 ---------------------
 crates/evmedia-core/src/full_export.rs             | 154 ----------
 17 files changed, 1827 deletions(-)
```

**怎么诊断的**：`git reset HEAD~2`（mixed）把**工作区**退回旧基线，
而 `crates/evmedia-contract/src/{args,lib}.rs`、`api.rs` 等文件当时**不在显式 `add` 的清单里**，
内容被退回旧版本；`git restore --source=…` 没把文件写回工作区，`git read-tree` 又留下混合树。
恢复**靠哈希而不是感觉**：用完整提交 `9bde721`（241 个文件）重建，
`git write-tree` 得到的树哈希 `a4c6559` 与之**完全相同**，
提交后 `git diff --name-status HEAD 9bde721` = **0 条**。

**当时提了什么 / 怎么解决**：从已知完好提交重建，按原始提交的**确切文件清单**
（`git show --name-only`）重建，不再手写清单；提交后比对树哈希。
顺带用 `git rm --cached` + `git commit --amend` 清掉恢复过程中被写回的 4 个旧 `ui/` 文件。

**影响面**：桌面端全部新代码 + 一批既有文件当场从磁盘消失，**差一步就是整批工作丢失**；
恢复之后还要靠树哈希证明「等于原样」。

**证据**：`git reset` 的根因自述、17 文件的差异现场、以及树哈希 `a4c6559` 的比对见存档。

**经验**：在这类仓库上**不要用 `git reset`（mixed）/`--hard`**。
动手前先记下 `git rev-parse 'HEAD^{tree}'`——它是一份**可验证的**回退锚点；
恢复时从完好提交重建，并用树哈希证明结果一致，而不是靠肉眼看文件在不在。
（同族的 `git commit -F <msgfile>`、`^{tree}` 需要单引号等，见 RETROSPECTIVE §12。）

### AGENT-06 · 一个控制进程把单项失败放大成整批失败，而且丢掉了日志

`batch` 2026-10 · `severity` high · `status` resolved · `source` codex--01a0b857:1043

**在哪里咬人**：GUI 的「全局 segment 队列」——一个控制进程调度全部选中视频，并启动 CLI。

**怎么暴露的**：用户**连续四轮**报「全部失败」，每轮都有一个不同的真实原因，
而第一轮连日志都没有：

> 全部下载失败 而且没有日志
> 全局队列退出：exit code: 2

**怎么诊断的**：五个原因依次被剥出来：

1. `exit code 2` 是 **clap 参数解析失败**、**不是**下载/解密失败——
   GUI 配置指向旧 CLI `target/release/evmedia.exe`，它不认识 `export-batch`，**联网前就退出**；
2. 全局队列把子进程 stdout/stderr **丢弃**，所以失败无迹可查；
3. 「一个成品已存在」被当成整批致命错误；
4. 单个视频签名 `tls handshake eof` 被升级成整批终止；
5. 单个 CDN 分段 `502 Bad Gateway` 让全局队列直接 `return`——**667 个任务因一个分段全灭**。

**当时提了什么 / 怎么解决**：**先把诊断链路修好**（stdout/stderr 落到每条任务与
`work/global-segment.log`），再逐条做失败隔离：已有成品自动跳过、单视频签名有限重试、
分段下载 3 次退避重试且最终失败**只影响所属视频**。分批解决并有回归测试。

**影响面**：用户付出了「修了一个 bug 出现一堆 bug」的代价；
而前三轮里原因是**不可观测的**，只能靠猜。

**证据**：四轮用户反馈与五个原因的定位过程见存档。

**经验**：批处理的第一条功能**不是隔离失败，而是让每个失败可观测**——
丢弃子进程 stderr 会让整批失败变成不可诊断。
另外：退出码要分清**哪一层**的错误（参数解析失败与业务失败都是非 0），
否则「全失败」会把排查引向业务逻辑，而真正的问题在启动参数。

### AGENT-07 · 代理与复核的断言，必须自己按行号复验

`batch` 2026-10 · `severity` high · `status` resolved · `source` claude-code--bc2b4335:338

**在哪里咬人**：采纳子代理（Review/Standards/复核）结论的环节。

**怎么暴露的**：代理自己制造过**三种幻影**：

1. 向 Standards 代理**谎称**一条注释规则是「仓库标准」→ 4 条发现被误标为硬违规
   （核实：该规则不在 `AGENTS.md` 里）；
2. 在 `domain.md` 里**编造了两个不存在的 ADR 文件名**和「ADR-0002」；
3. 复核代理把**已经跑通**的 `capture-ev` 标为「未验证」。

**怎么诊断的**：亲自按行号核实两条**会改变行动**的断言
（`scan.rs:105` 的 `active_keys()` 每轮读整个 `0x2a8` 对象含 `OFF_SCHEDULE=0x120`；
`regions()` 枚举后才做 4 MiB 分块读）——**都属实，但代理把 crate 名写错了**。
所以结论是「不能因为代理说得漂亮就采信」，也不能因为它写错一个名字就整体否定。

**当时提了什么 / 怎么解决**：把「按行号自己打开文件确认」变成采纳流程的一部分；
特别核实**它用来给你定违规的那条「标准」**本身是否存在。

**影响面**：与 VER-13 同族但更严重——VER-13 是审查报告**误报**，
这条是审查过程**发明事实**（编造的 ADR、编造的仓库标准）。
后者会让后续所有基于它的工作都建在不存在的东西上。

**证据**：三种幻影与两条被亲自核实的断言见存档。

**经验**：代理/复核输出**只当线索**。三条可执行的：
按行号打开文件确认；核实「标准/规范/先例」是否真实存在；
区分「结论错」与「描述细节错」（前者否定整条，后者只修正措辞）。
