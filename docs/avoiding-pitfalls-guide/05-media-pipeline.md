# 05 · 音视频解码与抓取

> 「解密成功」和「画面能看」是两件事，中间隔着一个解码器。

本节收录抓取与解码链路上的坑：实验被环境因素污染、屏幕捕获拿到别的窗口、
把「结构完整」当成「画面正确」。判据本身的问题归 `01-verification.md`，这里记的是**链路本身**的陷阱。

这一节的坑几乎全都会让观测失效而不是报错——它们不产生红色输出，只产生**看起来正常的错误数据**。

<a id="media-01"></a>
### MEDIA-01 · 播放器渲染在合成 GPU 表面上，`PrintWindow` 和 `BitBlt` 都读不到

`batch` 2026-10 · `severity` medium · `status` resolved · `source` claude-code--7b0c412f:2260

**在哪里咬人**：想通过截屏确认播放器在播什么、播到哪，用了 `PrintWindow` / `BitBlt`。

**怎么暴露的**：截图拿到的是别的东西（见 MEDIA-02），换方法之后才确认根本拿不到这一层。

**怎么诊断的**：

> Screenshots are a dead end — the player renders on a composited GPU surface that neither
> PrintWindow nor BitBlt can read.

播放器的视频面是**合成后的 GPU 表面**，不是 GDI 绘制的窗口内容，
所以两个抓窗口内容的 API 都只能拿到窗口的「壳」。

**当时提了什么**：放弃截屏，改用一条**决定性更强**的路：
用分片自己的签名 URL 去取一次，看**服务器**实际用哪把密钥下发。

**最后怎么解决**：截屏这条路被判定为死路，改走服务端侧的证据。

**影响面**：截屏是「直接看」的直觉做法，在这里它给出的不是错误数据而是**别人的画面**，
因此比报错更危险——它看起来像一次成功的观测。

**证据**：原话见存档。

**经验**：抓屏只对 GDI/软件渲染的窗口有效。遇到硬件合成（视频、游戏、DPI 缩放）时，
改用进程内的观测点（解码器、渲染器）或协议层证据——**先确认这条观测通道能看到目标**，
再拿它当证据。

<a id="media-02"></a>
### MEDIA-02 · `BitBlt` 抓到的是**遮住**播放器的那层窗口

`batch` 2026-10 · `severity` medium · `status` resolved · `source` claude-code--7b0c412f:2124

**在哪里咬人**：同样的截屏路线，换了个时刻。

**怎么暴露的**：截到的图内容不对，代理自己认出来「那是我的桌面」：

> That's my own desktop — the player is occluded at (1408,350) behind the foreground window,
> so BitBlt grabbed the covering app.

**怎么诊断的**：坐标 `(1408,350)` 处的播放器被前台窗口挡住了，
`BitBlt` 抓的是**屏幕像素**，于是抓到覆盖者。
同一次判断里还有个有价值的旁证：日志窗格仍在刷 `KEY set_enc…` / `H2 REQ POST`，
说明播放器**是活的**——「看起来是黑的」不等于「没有在跑」。

**当时提了什么**：先把播放器窗口提到前台再驱动它，否则一切截图都无意义。

**最后怎么解决**：改为主动把窗口前置（并把前置输入本身当成驱动手段，见下）。

**影响面**：与 MEDIA-01 叠加，一次「看一眼」的尝试会产生两个互相独立的错误结论。

**证据**：原话见存档。

**经验**：抓屏前先确认目标窗口**可见且未被遮挡**（`IsWindowVisible` + 前台窗口判断），
否则抓到的图必须当作无效数据丢弃。屏幕是共享资源，不是目标窗口的私有视图。

### MEDIA-03 · 注入解码器的实验被「窗口不在屏幕上」污染，明确不许从中记结论

`batch` 2026-10 · `severity` high · `status` open · `source` dsh--b94ed67a:40

**在哪里咬人**：把自建的解码包交给播放器自己的解码器（`inject_packet.py` / `inject_segment.py`），
想验证「播放器能不能解我们解出来的流」。

**怎么暴露的**：解码器**吞下了每一个注入单元**（60 个单元的返回值都等于注入大小），
但那些调用处读到的 AVFrame 是**空的**——而且同一窗口里，播放器**自己**的调用也没产出可读帧。

**怎么诊断的**：帧结构体给出 `width 1936, height 1088, format 53, stride 0, data 0x0`。
当时**播放器窗口不在屏幕上**（那台机器在跑游戏），所以「没有帧」有一个与实验无关的解释。

**当时提了什么**：把这条明确写成**被污染、必须在播放器真正渲染时重做**，
并留下了一条罕见的纪律：

> Do not record a conclusion from it.

**最后怎么解决**：未解决——实验待重做。这条被记为「未解决」而不是「已排除」。

**影响面**：这是本项目里**唯一一条主动拒绝出结论**的实验记录，价值就在这个拒绝上：
同一批观测（返回值=注入大小）如果被当成「解码器接受了我们的流」，
会立刻产出一个假的正面结论，并把后面几轮排查引到错误的方向。

**证据**：帧结构体数值与「confounded」判定见存档。

**经验**：实验有效性依赖的环境前提（窗口可见、进程活着、另一个仪器不在跑）要写在结果旁边。
一旦前提不成立，正确的输出是「**重做**」，不是「未观察到差异」——
后者会在下一次总结里变成「没有差异」。

<a id="media-04"></a>
### MEDIA-04 · 播放上下文会被回收，工具只能看到「活着的窗口」

`batch` 2026-10 · `severity` high · `status` open · `source` claude-code--7b0c412f:194

**在哪里咬人**：从播放器内存里收割分段密钥。

**怎么暴露的**：某个课时的密钥只收到一部分，剩下的怎么扫都没有。

**怎么诊断的**：**上下文对象是回收复用的**，工具在任意时刻只能看到**当前活着的那段窗口**：

> Context objects are recycled, so the tool only sees the live window at any moment (~70 keys);
> accumulation requires the user to actually play through.

**当时提了什么**：把「用户必须播一遍」写清楚，而不是继续找更聪明的扫描方式。

**最后怎么解决**：这一条后来**被推翻了**——因为密钥其实可以由
`MD5_hex(tk + 文件名 + "20220507")` 完全离线推导（见 [`docs/KEY-DERIVATION.md`](../KEY-DERIVATION.md)）。
但在**只能读内存**的那些路径（`grab` / `recover`）上，限制仍然成立。

**影响面**：一个「工具能力边界」被误判成「必须依赖用户操作」，
导致早期版本要求每节课播一遍。真正解除限制的不是更快的扫描，而是**换到了另一个数据来源**。

**证据**：原文见存档。

**经验**：当结论是「这个来源拿不全」时，下一步不是优化扫描，而是**问这个数据还有没有别的来源**。
回收/覆写的内存只能给出「此刻的窗口」；如果完整集合必须存在（否则播放器自己就不够用），
那它一定在别处——本地、服务端，或某个可推导的关系里。

### MEDIA-05 · 八个独立解码器实现表现一致，证伪「解码器版本」假设

`batch` 2026-10 · `severity` medium · `status` resolved · `source` dsh--b94ed67a:30

**在哪里咬人**：灰画面文件——同一份密文，密钥正确、结构正确，但解出来是平的灰色。

**怎么暴露的**：上一个会话把「解码器版本差异」记成了下一步实验（第 13.8 节）。

**怎么诊断的**：把**所有可用的实现**都跑一遍：
ffmpeg 8.1（86 条错误行、luma `mean 130.0 sd 0.00`）、ffmpeg 4.2.2（60–79 行、`mean 130.0`）、
`-threads 1`、`-err_detect ignore_err+careful`，以及机器上**其它六个**实现
（`h264_mf`、`h264_d3d11va`、`h264_dxva2`、`h264_qsv`、`h264_amf`、`h264_cuvid`）——
全部 `mean 130.0`、`sd ≈ 0`。ffmpeg 的报错是
`concealing 8160 DC, 8160 AC, 8160 MV errors in I frame`（120×68 个宏块全错）。

**八个独立实现失败得一模一样**，「解码器版本」假设因此被**证伪**。

**当时提了什么**：把假设正式记为「被推翻」，然后转向真正的解释——
播放器自己的软件解码器里**没有**标准 CABAC 表（`rangeTabLPS` / `lps_range` 在 DLL 里完全不存在），
却带着一套布局不同的表。

**最后怎么解决**：假设推翻；结论收敛为「level-40 那类分片由播放器自己的熵解码器保护」，
并且顺带划出了边界：level-51 与 level-42 的分片可以正常解密解码、可以导出，只有 level-40 这一类被卡住。

**影响面**：一个被写进文档、看起来最省事的下一步实验被一次性关掉，
省下的是「换一个 ffmpeg 版本再试一次」这类会反复回来的开销。

**证据**：八个实现的对照数值见存档。

**经验**：要让一个「实现差异」类假设死掉，就**穷举同一层里所有独立实现**：
当它们给出逐位相同的结果时，差异不可能在实现里。
这比再试一个版本强，因为它把假设**关掉**了而不是又推迟一轮。

### MEDIA-06 · 要播放器解密，就得给它**真实的前台输入**

`batch` 2026-10 · `severity` medium · `status` resolved · `source` claude-code--7b0c412f:2110

**在哪里咬人**：需要播放器**真的播放**某节课（解码才会产生分段密钥）。
但播放器窗口被遮住、也没有人在操作它。

**怎么暴露的**：先是截屏拿不到（MEDIA-01 / MEDIA-02），
然后发现「挂了钩子却什么都不来」，最后查清是**没人驱动播放**。

**怎么诊断的**：两条旁证先到位——

- 下载目录 3 分钟内 **211 个文件被重写** → 播放器在下载模式下运行，但**不解密**；
- 要求**真实前台输入**之后，一按下去密钥立刻开始流入（6687 并继续涨）。

后来固化成 `--sweep`：向窗口句柄 post **300 次 `VK_LEFT`**，
60 秒补齐最后 6 段，**259/259 全齐**。

**当时提了什么 / 怎么解决**：把「驱动播放」当成流水线的必要步骤，
用 `PostMessage(WM_KEYDOWN/WM_KEYUP)` 而不是模拟点击；并把它做成可复用的扫描（sweep）。

**影响面**：这是「收割密钥」这条路线的**前置条件**——
没有前台输入就没有解密，没有解密就没有密钥。
把「窗口不可见」误判成「播放器不工作」，会让整条路线看起来不可行。

**证据**：211 个文件被重写、输入一按密钥流入、以及 300 次按键补齐 259/259 见存档。

**经验**：被动等待一个 GUI 程序「自己做事」通常不会发生。
判据要分两步：**它在运行吗**（看文件写入、进程、日志），
**它在做我们要的那件事吗**（看目标事件流）。
两者都确认之后，再补上驱动——而且驱动要**真实**（前台输入 / 窗口消息），
不是「我以为它会自动开始」。
