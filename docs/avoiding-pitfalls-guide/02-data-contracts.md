# 02 · 数据契约、编码与格式

> 两个系统对同一个东西的表示不一致时，错误不会停在边界上，它会一路传播到最后的产物里，并以
> 「解不开 / 找不到 / 长度不对」的形式出现在完全无关的地方。

本节的坑分三类：**同一实体的两种表示**（32 个十六进制字符 vs 16 个原始字节）、
**同名不同物**（标题/文件名在层级化目录里重复）、**上游字段的语义**（排序方向、嵌套重复）。

### DATA-01 · 目录名在每一层重复，最长前缀匹配把 220 集全判成「不在 B 站」

`batch` 2026-10 · `severity` high · `status` resolved · `source` dsh--session-a48ac823:14942

**在哪里咬人**：`local_collection(video_path, collection_paths)`——把清单里的一集视频映射回
磁盘上的集合目录，再拿这个集合去 B 站找对应稿件。

**怎么暴露的**：WebGIS 课程的 **220 集全部**被报告为「不在 B 站上」。

**怎么诊断的**：平台清单在**每一层嵌套都重复集合自己的标题**。WebGIS 某一集的路径是

```
WebGIS课程 / WebGIS课程 / WebGIS课程 / WebGIS地理概念 / <episode>
```

而磁盘上的目录只有 `WebGIS课程/WebGIS地理概念`。按「取存在的最长前缀」匹配时，
每一集都解析成了最外层的 `WebGIS课程`——这个集合没有对应稿件，于是 220 集全部被判为缺失。

把它当成前缀问题会继续错：`["前端架构课程", "NestJS", "NestJS"]` 必须先读成
`["前端架构课程", "NestJS"]`，否则拿原始尾部去比 `("NestJS", "NestJS")` 什么也匹配不到，
**静默丢掉**这些集合的每一集。

**当时提了什么**：先折叠**相邻重复**的标题，再取存在的最长**后缀**（不是前缀）。

**最后怎么解决**：先折叠再按后缀长度从长到短试，命中即返回；找不到返回 `None` 而不是猜一个。

**影响面**：220 集被误报为缺失，而「不在 B 站」这个结论会直接驱动**重新上传**——
一次错误的匹配规则会变成几百个重复稿件。

**证据**：函数 docstring 与折叠逻辑见存档（第 14942–14964 行）。

**经验**：层级化的名字要按「路径段序列」处理，先归一化（折叠相邻重复）再匹配；
**取最长前缀是最容易写错的一步**——多数映射要的是后缀。匹配不到时必须返回「不知道」，
不能退回一个更浅的猜测，因为更浅的那个通常恰好存在，于是错误变得完全静默。

### DATA-02 · 章节化课程里的同名标题，被 `{title: duration}` 折叠成了一个

`batch` 2026-10 · `severity` high · `status` resolved · `source` dsh--session-d7528d99:7700

**在哪里咬人**：`verify_and_delete` 把 B 站某个稿件的分 P 列表读进一个 `{title: duration}` 字典。

**怎么暴露的**：第三章的本地文件被报告为「B 站上没有」，但它其实在。

**怎么诊断的**：`BV1zqhb6bE1W` 有两个分 P 都叫 `06. APIs`——第三章 ESLint 的 2729 秒
和第四章 Babel 的 1526 秒。字典只留得下后一个，于是第三章那个 2728 秒的文件
被拿去和**第四章的分 P**比时长，对不上，判为缺失。
这个形状在**每一门分章课程**里都会重复，因为每章都从 01 重新编号。

**当时提了什么**：标题映射到**时长列表**；一个文件只要与**同名分 P 中的任意一个**在容差内吻合就算通过。

**最后怎么解决**：`{title: duration}` 改为 `{title: [duration, ...]}`，
判据回到它本来该是的样子——同名且等长。

**影响面**：与 DATA-03 同源，两个 bug 叠加在同一个工具上。

**证据**：提交信息全文见存档（第 7700–7708 行）。

**经验**：任何 `{name: value}` 结构，在**名字来自分章/分册编号**的场景里都要先问一句
「这个名字唯一吗」。不能唯一时，结构必须是 `{name: [value, ...]}`，
而判据要相应改成「存在任意一个匹配」而不是「这一个匹配」。

### DATA-03 · 远端对象按裸文件名做键，覆盖掉另一章的 0.4 GB

`batch` 2026-10 · `severity` high · `status` resolved · `source` dsh--session-d7528d99:7711

**在哪里咬人**：`verify_and_delete` 里用于核对 R2 对象的 `remote map`，键是**裸文件名**。

**怎么暴露的**：两个文件（合计 0.4 GB）被报告为「不在 R2 上」，于是它们留在了磁盘上。

**怎么诊断的**：分章课程会重复文件名——`06. APIs.mp4` 在《前端工具链》的
第三章 ESLint（245 MB）和第四章 Babel（143 MB）下各有一份。
字典只留下了其中一个，于是**一个章节的文件被拿去和另一个章节的对象比大小**，
大小校验失败，判为不在 R2。

**当时提了什么**：改用上传器实际写入的键——`prefix + 相对集合的路径`；
裸文件名只作为回退，而且**仅当只有一个对象带这个名字**时才允许。

**最后怎么解决**：按 `prefix + 相对路径` 查，裸名回退加唯一性前置条件。

**影响面**：方向是安全的（只会误报「还需要」，不会误删），但结论仍然是错的：
0.4 GB 白白留在磁盘上，而两个平台其实都有。**「错在安全的方向」不等于可以接受**。

**证据**：提交信息全文见存档（第 7711–7719 行）。

**经验**：本地与远端要按**同一个键函数**对齐——直接用产生方（上传器）构造键的那个函数，
不要在读取方另写一条「看起来等价」的规则。任何以裸文件名为键的映射，
都要先证明「这个名字在这个集合里唯一」。

### DATA-04 · 密钥的两种表示：32 个十六进制字符**直接当 32 字节**用

`batch` 2026-10 · `severity` high · `status` resolved · `source` claude-code--7b0c412f:2026

**在哪里咬人**：AES-256 密钥的取用方式。

**怎么暴露的**：按「十六进制解码成 16 字节」的读法解不开；两种读法都试过之后才定案。

**怎么诊断的**：确认判据是取文件本身——
`[0]=0x47` 与 `[188]=0x47` 是合法的 MPEG-TS 同步字节，且后面跟着真实的 PES 头，
`triple.json` 里的那把密钥能打开磁盘上已下载的文件。

**当时提了什么**：写下结论「密钥就是那 32 个十六进制字符，作为 32 个 ASCII 字节使用（AES-256）；
按 16 原始字节读是错的」。

**最后怎么解决**：定案并写进 [`CONTEXT.md`](../../CONTEXT.md) 的术语表
（**Live key form** 与 **Stored key form** 两条）。

**影响面**：这是本项目的核心格式约定之一，任何一次搞混都会表现为
「解不开」而不是报错——错误信息完全指不到原因。`docs/RETROSPECTIVE.md` §5.8 记过同族的
另一个坑（`mask` 用 `MD5(filename)` 的原始摘要还是十六进制串前 16 字符）。

**经验**：「十六进制字符串」这个类型天然有两种解释，而**两种都不会报错**，
只会给出错误长度的密钥和一堆解不开的数据。凡是密钥/掩码/hash 以文本形式出现，
先在文档里写死它的字节解释，并在代码里用一个断言或类型名（而不是注释）固定下来。

### DATA-05 · 「清除已完成」用「保留未跑完」实现，失败与取消的行被一起删掉

`batch` 2026-10 · `severity` high · `status` resolved · `source` dsh--session-79bdf5ca:25190

**在哪里咬人**：`crates/evmedia-gui/src/queue.rs` 的 `clear_finished()`——GUI 上的「清除已完成」按钮。

**怎么暴露的**：用户实跑：导出 175 个、其中若干失败；点「清除已完成」后
**成功的、失败的、被停止的一起消失了**，「重试失败」按钮变成空操作，
失败的视频再也无法一键续传。

**怎么诊断的**：代码写的是

```rust
.retain(|entry| matches!(entry.status, JobStatus::Queued | JobStatus::Running));
```

它写的是「**保留还没跑完的**」。这和「**删掉已完成的**」**不是一回事**——
`Failed`（失败）和 `Cancelled`（被停止）既不在「没跑完」里，也不在「已完成」里，
它们是**你还欠着的活**。

而且仓库里那条测试的名字在撒谎：`clearing_removes_only_rows_that_are_done`
里只放了一行、而且那行是完成的，所以断言 `items.is_empty()`
对「正确实现」和「全删实现」**都成立**——零覆盖。

**当时提了什么**：先写混合状态测试（入队：完成/失败/取消/跳过/排队 五行 →
期望留下 失败、取消、排队 → 实际只剩排队 = FAILED），
再改成显式列出「什么算已完成」：

```rust
state.items.retain(|entry| {
    !matches!(entry.status, JobStatus::Complete | JobStatus::Skipped)
});
```

**最后怎么解决**：两个测试都过、GUI 16 项全过；
作者同时记录「修复还没生效，导出在跑、exe 被占用，不打断你的导出」——
这一点也值得记：**宣布修好与修好生效是两件事**。

**影响面**：批量导出里所有失败/取消的行被静默丢弃，
破坏了「重试失败」这条续传入口——**用户最需要它的时候正好失效**。

**证据**：代码、五行测试的期望/实际、以及修复后的 `retain` 见存档。

**经验**：集合过滤要写「**删除谁**」的白名单，不要写「保留谁」的补集——
补集会漏掉那些既不属于 A 也不属于 B 的状态（本案例里正是「失败」和「取消」）。
配套：测试名里承诺的场景必须在测试里**真的构造出来**；
一个只放一种状态的测试，无法区分「精确删除」与「全部删除」。

### DATA-06 · 一个字段漏改名：`duration_seconds` 过 IPC 仍是 snake_case，1910 行时长全空

`batch` 2026-10 · `severity` medium · `status` resolved · `source` dsh--session-79bdf5ca:8730

**在哪里咬人**：`crates/evmedia-gui/src/catalog.rs` 的 `VideoRef`——
GUI 与 CLI 之间的 IPC 目录结构。

**怎么暴露的**：界面时长列 1910 行全是「—」。启动日志直接给出信号：

```
INFO boot: player=true session=true catalog=true videos=1910 durations=0
sample={"id":"326523:905632","title":"02. 表现力的训练.mp4","duration":null,...}
```

**怎么诊断的**：`VideoRef` 用了 `#[serde(rename_all = "camelCase")]`，
但 `duration_seconds` **仍然是 snake_case**，前端读 `durationSeconds` 得到 `null`。
字段类型是 `Option<f64>`，所以缺失**不报错**——静默变成 `null`。

**当时提了什么**：序列化侧 `#[serde(rename = "durationSeconds")]`，
反序列化侧用双名兼容（CLI 写 `duration_seconds`、前端要 `durationSeconds`，两边都要），
并加一条防漂移测试。

**最后怎么解决**：已解决；新增测试 `every_field_keeps_its_name_through_the_wire`，
**并在 fix 过程中被它自己抓了一次**
（`the view reads durationSeconds: {"durationSeconds":null,...}`）。
一个关键细节：`rename_all` 同时影响读和写，所以读写名字必须分开声明。

**影响面**：全量目录 UI 的一个关键列静默失效。
`Option` 类型把它从「报错」变成了「无声的 null」，这正是可选字段最容易藏 bug 的地方。

**证据**：启动日志、根因结论、以及防护测试自己报出的失败见存档。

**经验**：跨序列化边界给**每个字段**都加「名字不漂移」的测试，
不要相信 `rename_all` 的覆盖面（它对 `rename` 过的字段、以及单独改名的字段无效）。
更一般的规则：**字段缺失不报错**的边界，必须有一条测试专门钉住字段名。

### DATA-08 · `export-evs` 成功退出却不发 `finished` 事件，按契约每一行成功都被判失败

`batch` 2026-10 · `severity` high · `status` resolved · `source` dsh--session-79bdf5ca:9447

**在哪里咬人**：`crates/evmedia/src/main.rs` 与 `crates/evmedia-contract/src/report.rs`，
契约写在 [`docs/CLI-CONTRACT.md`](../CLI-CONTRACT.md)。

**怎么暴露的**：用户：「为什么全是失败啊？？？？ 而且还停止不了」——
**每个成功导出的视频都被标红**。

**怎么诊断的**：`export-evs` 成功退出时**根本不发 `finished` 事件**：
stdout 停在 `stage download end`，然后退出码 0，没有结论。
而窗口是**严格照契约办**的——「没有报告完成状态就是失败」，
这条不能松，因为 `partial` 会留下一个看起来完整其实是残的文件。
于是：契约正确 + 生产者漏发 = 每一次成功都被读成失败。

**当时提了什么**：在 `main` 里为所有不自报结果的子命令**兜底补发** `Finished{Complete}`，
用 `Reporter::finished()` 记录「是否已自报」；`grab` 那种自己会报 partial/cancelled 的不受影响。

**最后怎么解决**：已解决；实测修复后 stdout 末尾出现

```json
{"event":"stage","name":"download","state":"end","detail":"11/11 segment(s) of 11"}
{"event":"finished","status":"complete","exit_code":0,"message":""}   ← 以前没有这行
```

123 项测试全绿。

**影响面**：整个批量导出的成败判定被**反转**，用户无法信任任何一行状态；
并且这个显眼的故障**掩盖了「停止没反应」这条独立问题**。

**证据**：修复前后的 stdout 结尾见存档。

**经验**：事件流契约的**终止事件**要么由框架统一兜底补发，要么用测试钉住**每个**子命令的输出结尾。
「生产者忘记发终止事件」与「任务真的失败」在消费者看来完全一样，
所以这个漏洞不能靠约定，只能靠兜底或测试。
附带一条：一个响亮而错误的故障会掩盖旁边那个安静的真故障。

### DATA-09 · 把「不在我的对照表里」读成「没上传过」，差点据此删掉 255 GB

`batch` 2026-10 · `severity` high · `status` resolved · `source` dsh--session-a48ac823:17850

**在哪里咬人**：`work/` 清理工具的分组标签与删除建议。

**怎么暴露的**：控制台输出把 883 个目录 / 243.00 GB 归为「不属于任何已知合集」，
代理据此**准备提出大批量删除**。

**怎么诊断的**：代理自行纠正了措辞——
那句标签的真实含义是「**不在我的对照表里，无法判定**」，不等于没上传过。
继续查 B 站实时稿件列表，发现表里缺的 6 个合集
（微前端架构实战、CSS企业应用方案、微前端、工程管理实战、D3.js、前端测试框架）**真实存在**，
正是 243 GB 的大头。

**当时提了什么**：先拿完整稿件清单补齐映射，再决定删什么。

**最后怎么解决**：补齐 `R2_BY_COLLECTION` / `BILI_BY_COLLECTION`；
此后新增 `sync_bili_ids.py` 每轮自动补登新稿件 id。

**影响面**：若按错误标签执行，会清掉 243 GB 在 B 站上有价值、
仅因**未登记**而「不可判定」的 work 缓存。一个措辞问题直接站在不可逆删除的上游。

**证据**：控制台输出与「6 个合集真实存在」的核对见存档。

**经验**：报表里的**未知态必须显式叫「无法判定」**，
绝不能用「不存在」的措辞承载「我表里没有」。这两者在代码里可以是同一个分支，
但在**给人看的输出里必须是两句话**——
因为读它的人（或 agent）下一步动作完全不同：一个去查表，一个去删除。

### DATA-12 · `evs_playkey` 与 `descriptor.cache_key` 只在**一条**流程里相等

`batch` 2026-10 · `severity` medium · `status` resolved · `source` dsh--7276b720:5197

**在哪里咬人**：在线重取清单的请求参数——`evs_playkey` 的取值来源。

**怎么暴露的**：用 `cache_key` 形态的 `evs_2026_…` 串去请求，服务器回

```
errcode -1: illegal base64 data at input byte 3
```

**怎么诊断的**：API 要的是 **base64 形态**（如 `V4bsTWiO…`）而不是 `evs_2026_…` 形式；
所以「`evs_playkey == descriptor.cache_key`」**只在 20260515 那条流程成立**——
代理主动更正了自己此前写进文档的简化说法。
同一轮还确认：一次请求塞 195 个分段名，服务器**全签了**，
包括那 190 个属于**另一节课**的名字——**它不校验名字是否属于该 playkey 的课程**。
反过来，用错误的 playkey 拿到的 `tk` 解出来同步率只有 **0.13%–0.29%**（会响亮报错，不会悄悄骗过去）。

**当时提了什么 / 怎么解决**：把 `evs_playkey` 与 `cache_key` 分开处理；
并记录「服务器照签不代表名字属于该课」——它直接影响「在线重取清单」能不能给任意文件签名。

**影响面**：这条等价关系**至今仍写在
[`docs/RETROSPECTIVE.md`](../RETROSPECTIVE.md) §3.4 里**，会误导下一个 agent。
**建议顺手更正那一行**（本指南不改动既有文档，只在此登记）。

**证据**：服务器的报错、「195 个名字全签」与「错误 playkey 同步率 0.13%–0.29%」见存档。

**经验**：两种**看起来同样的串**（base64 形态 vs 前缀形态）是两个字段。
不要把**一次观测**上升成**字段等价**——观测只覆盖它当时那条流程；
写进文档时要带上它成立的条件（哪条流程、哪个版本）。

<a id="data-13"></a>
### DATA-13 · 密钥来源的模型错了两次：不走 OpenSSL，且捕获是**陈旧**的

`batch` 2026-10 · `severity` high · `status` resolved · `source` claude-code--7b0c412f:3890

**在哪里咬人**：找「分片解密用的 AES」以及「为什么候选表里一把都不中」。

**怎么暴露的**：钩 OpenSSL 的 `AES_set_encrypt_key`（RVA `0x791F90`）
抓到 **24390 个 AES-256 密钥** → 却 **0/847 分片、0/52 params** 命中。

**怎么诊断的**：两条独立的错误被分开：

1. **作用域错了**：分片解密**不走 OpenSSL**——
   它在 `0x39080` 先按 `ctx+0x268` 的掩码做 16 字节周期 XOR 再 AES；
   标准 MD5 的 K 表（`0xae1ed0`）**没有任何代码引用**。
   「抓到密码学材料」不等于「抓到目标用途」。
2. **数据陈旧**：`find_aes_key.py` 的 155306 个候选 0 匹配，
   原因是捕获时 pid 是 1488、而当前是 12788——**会话密钥已随进程轮换**。
   同一类证据：下载**不产生**密钥（只下载 0 命中，播放时 534 命中）；
   「211 个文件被重写……却零次 AES 密钥安装」。

**当时提了什么 / 怎么解决**：把「密钥来源」的模型从「OpenSSL 全局」改为
「分片路径自己的 XOR+AES」；捕获与样本必须**同一进程/同一次会话**。
（纯离线推密钥在这个阶段仍未解决。）

**影响面**：这是本项目的核心问题之一，两个错误模型各自都能解释「为什么什么都没找到」，
而它们的修法完全不同（改钩点 vs 重抓）。

**证据**：`24390 → 0/847`、`155306 → 0`、pid 1488 → 12788 的轮换见存档。

**经验**：抓到**密码学材料** ≠ 抓到**目标用途**——
必须用**已知答案**做双向命中检验（一把已知正确的密钥必须能被判据认出来）。
另外：会话级密钥会**随进程生命周期轮换**，
所以「候选表 0 命中」的第一个怀疑对象应该是**捕获是否已经过期**，
而不是「这个算法不对」。
