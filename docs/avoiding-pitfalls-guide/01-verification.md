# 01 · 验证方法与证据强度

> 判据本身错了，比不做验证更糟：它会给出一个可以被引用、被写进文档、被下游信任的结论。

这一节收录的全是**判据出问题**的实例，而不是「代码有 bug」。共同的形状是：
一个检查看起来通过了，于是结论被写下来，后来的事实推翻了它，而复盘时发现那个检查从一开始
就不可能区分「对」和「看起来对」。因此每条都特别记了「当时是怎么被当成证据的」。

与 [`docs/RETROSPECTIVE.md`](../RETROSPECTIVE.md) §6.1（不可信的检查）的分工：
那一节列的是**判据清单**（TS 同步字节、ffprobe、端口在听……），
本节收录的是**具体的翻车事件**——哪一次、谁、因此得出了什么错结论、多久之后才纠正。

### VER-01 · 探针的读取长度不满足所有对齐要求，于是「全部 0 命中」

`batch` 2026-10 · `severity` high · `status` resolved · `source` claude-code--1b8d953d:2349

**在哪里咬人**：读播放器内存里 32 字节 AES 密钥调度槽的探针，缓冲区长度取 `188 × 2 = 376`。

**怎么暴露的**：所有暴力搜索都返回「0 命中」，看上去是一个干净利落的否定结论——
「这个槽位不存密钥」。它被写进结论，并且据此把该代码路径删掉了。

**怎么诊断的**：`376` 是 188 的整数倍，但**不是 16 的整数倍**。AES 按 16 字节块读取，
越界的读抛出的异常被吞掉了，于是每一次探测都静默失败，返回 0 命中。
正确的长度是 `188 × 4 = 752`，188 与 16 的最小公倍数。

**当时提了什么**：改成 752，并在探针里不再吞异常。

**最后怎么解决**：改了长度之后，探针读到 333 个已填槽位，重建出 333 把密钥，333 个分片全部打开、0 失败；
第二次跑 369/369。播放上下文 `+0x120` 的调度槽**确实是密钥来源**，此前那个「不是」的结论是仪器的产物。

**影响面**：此前所有「0 命中」结果全部作废；一条真正在工作的代码路径被删除，后来靠注释和
`tools/parser-tools/probe_schedule_key.py` 才恢复。这类损失不进测试、不进编译错误，只进结论。

**证据**：同一段总结里还并列写着「376 是 188×2 但不是 16 的倍数」和「这条 bug 使此前所有暴力搜索的
0 命中结果作废，并传递性地得出了错误的结论」。见下方存档。

**经验**：探针的读取长度必须同时满足**所有**参与方的对齐要求；「全部 0 命中」先怀疑仪器，再怀疑假设。
一个否定结论只有在仪器被证明是活的之后才有资格被记录。

### VER-02 · 一个本身坏掉的测试，删掉了一条真正在工作的代码路径

`batch` 2026-10 · `severity` high · `status` resolved · `source` dsh--session-e3e25c56:2157

**在哪里咬人**：`schedule_to_key()`——从播放上下文的 32 字节调度槽还原 32 字符十六进制密钥的函数。

**怎么暴露的**：它曾经被删除，理由是「有一个测试证明这个槽位不存密钥」。

**怎么诊断的**：那个测试本身就是坏的（其失败原因与「槽位是否存密钥」无关，属于 VER-01 同一类仪器缺陷）。
换成直接对活播放器测量：333 个上下文填了槽位 → 333 把密钥重建 → 333 个分片打开、0 失败。

**当时提了什么**：把该函数恢复，并在文档注释里写明它的结论强度与测量方式。

**最后怎么解决**：函数恢复，注释里留下了这段被踩过的记录：

> This **is** a key source, and it was wrongly deleted once on the strength of a test that was
> itself broken.

**影响面**：一次错误删除，加上一个「本来可以更早拿到的能力」被推迟。恢复成本不高，
但**删除动作本身是不可逆的**——如果当时没有另一条独立测量，这条路径就永久消失了。

**证据**：函数注释与实测计数（333/333、369/369）见存档。

**经验**：删除代码前先证明「判定它没用的那个测试」是好的。做法是 mutation test——
把修复回滚，确认测试确实失败；测试不会因为修复而变红，就没有资格判决任何代码的生死。

### VER-03 · 仪器的静默被读成「目标没有发生」——三个独立机制都产生同一种静默

`batch` 2026-10 · `severity` high · `status` resolved · `source` claude-code--bc2b4335:304 ; dsh--session-e3e25c56:575 ; dsh--session-e3e25c56:23774

这是本批次里**复发最多**的一类错误，三个会话各自独立踩了一次，机制各不相同：

**(a) 打印上限 + 心跳饥饿**（`probe_write.py`）。跑到约 40 条访问报告之后输出彻底安静，
安静被读成「播放器在这段时间没有写这个页」，并据此写下了结论。
对抗性验证（17 个 agent、3 票全部反驳成功）指出：这段静默**不能区分**
「仪器还活着但在限流」和「仪器已经死了」。两个机制都能产生同样的静默：
打印上限 `INDIVIDUAL_CAP=40`（`probe_write.py:93/:251`），以及唯一的心跳（`still watching`）被饿死。

**(b) `PAGE_GUARD` 被第一次访问消费掉**（同一个 `probe_write.py` 的前身）。两次运行都是
「armed 成功、240 秒零事件」（491 个 context/438 个空 key 字段；938 个/872 个），看起来像「播放器根本没写」。
真实机制是：Frida 的 `MemoryAccessMonitor` 靠 `PAGE_GUARD`，而**guard 被第一次访问（读或写都算）
消费后不会自动恢复**；播放器高频读这些对象，回调第一次触发时看到 `d.operation !== 'write'` 就返回，
页面从此再无保护，剩下 240 秒全盲。原话把结论钉得很准：

> It was never "the player did not write"; it was "nothing was reported".

同一轮还量出两个配套缺陷：打印上限用 `return` **短路了处理逻辑**（600 条之后永久失聪）；
重挂定时器 100 ms 太慢——实测「不重挂」抓到 **0/24**，「100 ms 定时器」抓到 **23/24**，
必须用 `setTimeout(...,0)` 从回调内重挂。

**(c) 脚本顶层抛异常，静默废掉整份钩子**（`capture_playback.py`）。用户明确说「一直在播放」，
而探针零事件、输出文件 1 字节 / 0 字节。代理先假设「是不是播放器换进程了」去列进程，
最后才发现：这个 Frida 版本里 `Module.getExportByName` 已不是函数，
它在脚本**开头**抛异常，**写在它后面的所有钩子都没挂上**。修掉后同一播放器 60 秒内给出 1760 个解码包。
教训被写进提交信息：**探针报「什么都没有」时，先怀疑探针**。

**最后怎么解决**：三个会话各自修掉了各自的机制——结论被降级、上限改为只抑制打印、
`setTimeout(...,0)` 重挂、`getExportByName` 修好并把「钩子必须自报 armed」写进探针契约。
修复方向里最值得抄的一条是：**重装必须限速，并且要有一个不依赖那个定时器本身的心跳，
否则它永远无法报告自己死了**。

**影响面**：这是一个「用静默当作证据」的范本，而且是本批次里**唯一一个在三个会话里独立复发的机制**。
其中 (b) 尤其值得记住，因为它的表现最像「目标没做这件事」，
而它实际上是**探针在第一次访问之后就已经失明**。

**证据**：`surviving` 判定与三条 corrections（(a)）、guard 被消费的说明与 0/24 vs 23/24 的实测（(b)）、
用户原话与「60 秒内 1760 个解码包」（(c)）见存档。

**经验**：**仪器的静默永远只说明「仪器不知道」**。要断言「世界没有发生」，先证明仪器活着；
而仪器的存活信号不能依赖它自己正在监视的那条路径——否则它无法报告自己已死。
三条落地做法：静默类结论**先做一次「已知必中」的对照测量**；
断点/监视器的上限只许抑制**输出**，不许短路**处理**；
脚本顶层任何异常都要让整份探针**显式失败**，而不是安静地少挂几个钩子。

### VER-04 · 探针的命中上限与去重，把热指令伪装成「只命中一次」

`batch` 2026-10 · `severity` medium · `status` resolved · `source` claude-code--1b8d953d:4421

**在哪里咬人**：用 `probe_at.py` 判断 `0x792c78` 是不是 AES 的 AddRoundKey，看到「只命中一次」，
于是认为这是一条冷路径。

**怎么暴露的**：对抗性复核把这个「单次命中」判为**探针的产物**，不是频率证据：
`MAX_HITS=30` 限制了收集量，Python 侧又按 `(rva, ts, hex, regs)` 去重，
所以一条在重复帧上被反复执行的指令**只会打印一行**。

**怎么诊断的**：回到文件本身逐字节核对，发现更大的问题——`0x792c78` 处的字节是
`33 6e f8 = xor ebp,[rsi-8]`，读 S 盒的指令其实在它前面一条（`0x792c59`）。
`.pdata` 里包含它的范围 `[0x792b1c, 0x792ec3)` 是**链式 `.pdata` 片段**，
真正的函数入口是 `0x791F90 = OpenSSL AES_set_encrypt_key`。所以：

1. 钩这里读到的是**密钥编排**的调用约定，不是想要的块加密；
2. `KeyExpansion` 对每一次 OpenSSL AES 使用都会跑（包括 TLS 的 curl/libavformat http），
   所以栈上那些分片形状的字符串（`0|0|<uuid>.ts` 缓存键、清单 base URL、FFmpeg 的
   `…' for reading` 错误片段、`Authorization`）**并不能把 AES 定位到分片解密路径**。

**当时提了什么**：停止把 `0x792c78` 当预言机；改钩应用自己的 AES 密钥编排 `0x20EC0`，
并输出原始寄存器 + 返回地址/回溯，而不是只打印「指向可打印字符串的寄存器」。

**最后怎么解决**：预言机站点更换；`probe_at.py` 的能力缺口被明确记录
（它拿不到调用约定：没有 `Thread.backtrace`、不定位外层入口）。

**影响面**：一个「低频」印象差点变成「这条路径不重要」的判断。附带教训：
`scan back for cc cc cc` 这类经验性配方此处给出了正确入口 `0x791F90`，
但**配方对了不代表推理对了**——它和链式 `.pdata` 是两种解释，必须用文件字节定案。

**证据**：`synthesis.probe_at_conclusion` 全文见存档。

**经验**：探针的**聚合口径**（上限、去重键、打印格式）要写在结论旁边。
命中数不是频次，去重后的「1」往往只是「很多，但我只留一个」。

### VER-05 · 两个仪器同时挂在同一个进程上，观测互相污染

`batch` 2026-10 · `severity` medium · `status` resolved · `source` claude-code--bc2b4335:302

**在哪里咬人**：终端 2 跑 `evmedia.exe grab --pid 6684`，同时探针也挂在同一个 pid 6684 上。

**怎么暴露的**：出现了异常密集的页面访问风暴，一度被当成播放器的真实行为来解读。

**怎么诊断的**：probe 在被监视页上设 `PAGE_GUARD`，而 `grab` 在全内存反复扫描——
**扫内存就是读内存，读到带 guard 的页就会触发 probe 的回调**，
probe 每次回调又对整个 24 页做一次 `disable()` + `enable()`。两个仪器因此互相放大。

同一段里还有一个更普遍的问题：工单把「重装」记为免费（100.4% 吞吐），
但那是在**单线程替身、1 个页**上测的；这里是**16 线程的真实 Qt 播放器 + 24 个页 + 另一个进程在狂扫**。

**当时提了什么**：下次不要让 probe 和 grab 同时跑同一个 pid；重装必须限速。

**最后怎么解决**：作为「两个立刻可用的东西」记录下来并执行。原话把根因总结成一句更值得记住的话：

> 变量变了，那个结论不能外推——这正是这个项目反复吃亏的那种「结论活得比证据久」。

**影响面**：一次观测风暴被误读成目标程序的行为。这类错误特别贵，因为它**看起来像新发现**，
而实际上只是自己的两个探针在打架。

**证据**：第 302 行（两个仪器同 pid 的机制）与第 304 行（结论外推的边界）见存档。

**经验**：**观测者会改变被观测对象**。同一进程上只挂一个侵入式仪器；
性能类结论必须连同它的测量条件一起记录——单线程、1 个页的吞吐数字不能外推到 16 线程、24 个页。

会让「齐了」这个事件在错误的时刻发生。

### VER-08 · 把 `exit 0` 当成功：空匹配、漏传、过期缓存都报「通过」

`batch` 2026-10 · `severity` medium · `status` resolved · `source` dsh--session-a48ac823:17455

**在哪里咬人**：会话收尾时代理主动列的「Errors and Fixes」清单，三处同源：

1. `powershell -File backgrounds.ps1 -Key a,b` **一张卡片都没匹配到，却报告成功**；
2. 看门狗 `exit 0` 被当成「全部传满」（见 VER-06）；
3. `clean_work.py` 读的 `bili-parts.json` 缺新 BV 号，把**所有**内容报成 `not on B站`。

**怎么诊断的**：退出码与副作用**脱钩**了——0 只代表进程没崩，
不代表它承诺的那件事在远端可观测。配套修法是「空匹配时大声失败退出」、
「读取失败硬失败而不是返回 0 条」、「用分 P 标题逐条比对而不是比数量」。

### VER-11 · PE 文件的**偏移**不是它的 **RVA**

`batch` 2026-10 · `severity` medium · `status` resolved · `source` dsh--b94ed67a:38

**在哪里咬人**：把磁盘上的 DLL 与内存里已加载的模块做字节比对。

**怎么暴露的**：比较 `disk[0xB9648]` 与 `module_base + 0xB9648` 时字节不同，
现象直接指向一个**关于目标本身的错误结论**：「加载的镜像不是这个文件」。

**怎么诊断的**：`0xB9648` 是 **RVA**，磁盘文件里要按节表映射才能取到对应字节
（`tools/parser-tools/dump_cabac_tables.py` 做了这件事），映射后确认是同一个文件。
该 DLL 的节表：

```
.text   rva 0x1000      .rdata  rva 0x7fc000   .data  rva 0xbb5000
.pdata  rva 0x12a8000   .rsrc   rva 0x12e2000  .reloc rva 0x12e3000
```

**当时提了什么**：把这条**当作测量错误记录下来，以免重复**（作者原话：
「A measurement error worth recording so it is not repeated」）。

**最后怎么解决**：改用节表映射后比对，结论从「不是同一个文件」纠正为「是同一个文件」。

**影响面**：这类错误会让整个逆向方向跑偏——它会让你去怀疑目标被替换/加壳，

（见 [`docs/RETROSPECTIVE.md`](../RETROSPECTIVE.md) §12 第 5 条），是同一个坑的另一面。

**证据**：节表数值与「映射后是同一个文件」的结论见存档。

**经验**：**文件偏移、RVA、虚拟地址是三个不同的东西**。
做「磁盘 vs 内存」比对前先明确自己在用哪一个；
一次字节不一致首先怀疑取址，最后才怀疑目标被换过。

### VER-15 · 命中数正好等于随机期望值，差点宣布攻破
